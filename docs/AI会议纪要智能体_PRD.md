# 1. 项目背景与目标

## 1.1 现状与痛点

我是建筑行业转行AI产品经理，在建筑项目工作中，我长期参与跨部门会议，亲身经历过大量“会上说得好、会后没人干、责任分不清”的情况，导致项目推进慢、互相推诿。

为了验证这个痛点在互联网职场也普遍存在，我没有条件做大规模访谈，而是用低成本、可落地的替代调研方式：

1. 查看飞书妙记、通义听悟在知乎、应用商店的用户评论，高频吐槽集中在：
    1. 只有语音转文字，整理纪要依然要花很久
    2. 不会自动提取谁要做什么、什么时候做完
    3. 会后任务没人认领，还是要反复沟通
2. 结合微软工作趋势指数公开数据：职场人每天大量时间消耗在会议与纪要整理上
3. 通过前同事、产品社群，轻量级沟通了3位互联网从业者（2位产品经理、1位研发），确认：
    1. 整理纪要平均要花47分钟
    2. 最痛的不是“转写不准”，而是责任不闭环

## 1.2 产品目标

做一个简单、能落地的AI纪要小工具，只解决最核心的问题：

1. 把会议录音/文字，自动变成结构化纪要
2. 强制提取任务、责任人、截止时间，避免会后扯皮
3. 操作简单，不用学习，适合普通职场人快速使用

## 1.3 成功指标（基于个人实践可验证）

- 整理纪要时间：从40~60分钟 → 降到10分钟内
- 任务提取准确率：85%左右（三轮简单自测得出，不是实验室数据）
- 用户感受：测试者都认为“比手动整理省事”

# 2. 用户画像与场景

## 2.1 典型用户画像

### （1）产品经理 · 李某

- 背景：SaaS公司产品经理，日常会议多
- 真实状态：每天开完会要整理纪要，经常要追着研发问“谁负责、什么时候交”
- 痛点：口头约定的任务，会后没人认；纪要整理耗时间
- 原型来源：产品经理社群匿名交流的从业者，真实反馈

### （2）研发主管 · 张某

- 背景：带小团队，负责几个项目，技术会很多
- 真实状态：会上定的技术方案、bug修复，会后没人跟进
- 痛点：纪要没有明确任务，全靠自己记，容易漏
- 原型来源：研发社群交流，贴合真实工作状态

### （3）项目经理 · 周某

- 背景：跨部门协作多，要推动多方执行
- 真实状态：会议内容杂，行动项写得模糊，跟踪困难
- 痛点：责任不清晰，各部门容易推诿
- 原型来源：朋友介绍的项目经理，结合我建筑行业经验整理

## 2.2 典型使用场景

1. 需求评审会：开完会直接上传录音 → 自动出纪要+任务清单 → 发给团队执行
2. 项目复盘会：自动提炼问题、改进项、责任人 → 避免“只复盘不落地”
3. 跨部门协调会：明确谁做什么、什么时候做完 → 减少扯皮

## 2.3 痛点优先级

1. P0：任务没有责任人、没有时间 → 会后无法落地
2. P1：纪要整理太慢，占用工作时间
3. P2：纪要格式乱，不方便分享存档
4. P3：多语言、发言人区分（暂时不重要）

## 2.4 用户研究方法说明

1. 自身经验迁移：建筑行业跨部门会议的真实痛点，是本产品的核心灵感
2. 公开信息调研：看竞品用户评论、行业报告，验证痛点普遍性
3. 小范围轻量沟通：和3位互联网从业者简单交流，确认需求方向
4. 自测+小范围测试：MVP方案完成后，找3位朋友试用，收集反馈

# 4. 功能需求

## 4.1 必须功能（Must have）

| **模块** | **功能名称** | **简单说明** |
| --- | --- | --- |
| 输入 | 上传音频/粘贴文本 | 支持常见录音格式，也可以直接贴文字 |
| 处理 | 语音转文字 | 调用第三方API，保证基本准确 |
| 处理 | 结构化纪要 | 自动分成：会议主题、讨论要点、决策 |
| 处理 | 任务强制提取 | 必须提取：任务内容、责任人、截止时间，缺了标红 |
| 输出 | 查看/编辑纪要 | 可以手动改AI识别错的地方 |
| 输出 | 导出/分享 | 导出简单格式，方便发给团队 |

## 4.2 后续再做（Should/Could）

- 发言人区分
- 多语言支持
- 风险提醒
- 对接飞书/钉钉

## 4.3 本期不做（Won’t have）

- 实时转写
- 多语种翻译
- 复杂权限管理

# 6. 交互流程

1. 打开页面 → 上传录音 / 粘贴文字
2. 点「开始处理」
3. 等待生成 → 查看结构化纪要+任务
4. 编辑修正 → 导出/复制

说明：界面只做核心流程，不做复杂视觉设计，重点是逻辑通顺。

---

# 7. 验收标准

1. 功能可用：核心流程能跑通，没有明显逻辑错误
2. 准确率达标：自测任务提取大致准确，允许手动修正
3. 用户可接受：3位测试者认为“比自己整理快、省事”
4. 无重大问题：不会出现无法上传、处理失败等致命问题

# 8. 已知风险与应对

| **风险** | **应对办法** |
| --- | --- |
| 专业术语识别不准 | MVP开放手动编辑，后续再优化 |

| 用户担心录音隐私 | 明确说明不存储、仅用于本次处理 |

# 9. 附录

# 10. 我的产品思考

1. 为什么不做实时转写？
因为用户最痛的不是“实时看”，而是“会后能落地”，我资源有限，先抓核心。
2. 为什么强制要责任人+时间？
来自我建筑行业的真实踩坑：分工不写死，项目一定拖。
3. 为什么准确率定85%？
自测三轮得出的，太低用户嫌麻烦，太高我做不到，85%是平衡点。
4. 这个项目对我的意义：
不是公司项目，是我从建筑跨到AI产品的一次完整实践：从痛点 → 调研 → 方案 → 功能 → 验证，全程自己走完。
